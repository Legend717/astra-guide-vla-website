Technical report

Can Astra Guide a VLA to Solve RoboMME?

A Self-Evolving Harness for Memory-Dependent Manipulation

Read as PDF ↗

Abstract

Robot manipulation often requires information from past observations to guide current actions. We present a self-evolving harness that combines GPT-6 Astra with the official RoboMME GroundSG vision-language-action model (VLA) for memory-dependent manipulation. Astra interprets task history and selects subgoals, while the VLA handles their execution. To reduce repeated supervision, Astra chooses how many control steps the VLA may execute before review and can select robot-state monitors that prompt earlier inspection. It also intervenes directly when execution requires correction. Starting from subtask-duration priors, the harness accumulates and revises experience across episodes. This experience informs when Astra can rely on the VLA and when closer supervision is needed, while VLA weights remain fixed. Across 800 test episodes covering all 16 RoboMME tasks, the system achieves 97.1% success, with 54.9% of control steps executed without additional Astra review. These results show that high task success can coexist with less frequent supervision, supporting experience-guided coordination as a practical way to combine VLM reasoning with learned robot control.

1 Introduction

In robotic manipulation, deciding what to do next often requires information from past observations. A robot may need to remember which container hides a target, count earlier events, or reproduce a demonstrated action sequence. RoboMME evaluates these capabilities through 16 tasks grouped into counting, permanence, reference, and imitation [6]. Solving them requires both interpreting the relevant history and executing actions consistent with it.

Recent RoboMME studies use GPT-6 Astra (hereafter Astra), a vision-language reasoning model, in two distinct roles. Direct control asks Astra to generate robot motion targets from visual history, placing action generation as well as task reasoning in the model and incurring repeated inference during execution [12]. A three-tier system instead uses Astra to plan subgoals for a trained vision-language-action model (VLA), with a separate learned monitor tracking completion [3]. This division reduces Astra’s involvement in routine motion, but concentrates its role on planning. We seek to retain the efficiency of learned control while also using Astra to supervise progress and intervene when execution goes wrong.

Reviewing every short action sequence, or action chunk, incurs repeated inference cost even when the VLA is still executing the same subgoal. Longer intervals between reviews can delay correction of a failed grasp or an incorrect motion. Appropriate supervision therefore depends on the current task stage, visual evidence, and the controller’s behavior in similar situations. Experience from earlier episodes can help guide these decisions, but must be updated when new outcomes reveal its limitations.

We present a self-evolving harness in which Astra learns from execution experience how to supervise the official RoboMME GroundSG VLA (Figure 1). Given task history and current observations, Astra selects a subgoal and a finite execution budget. When permitting a longer interval, it can activate auxiliary monitors, such as gripper-state or directional-motion checks, to trigger review before the budget expires. The VLA continues to react to the latest observations throughout this interval. At review, Astra decides whether to continue execution, revise the subgoal, or intervene directly. Post-episode reflection revises advice about these choices, progressively informing supervision without changing VLA weights.

We evaluate the harness on all 16 RoboMME tasks with 50 episodes per task. It achieves 97.1% success across 800 episodes, reaches at least 90% on every task, and executes 54.9% of control steps without additional Astra review. Execution and experience traces show how prior outcomes lead to revised review intervals and more specific task interpretations. Together, these results and traces illustrate how experience can guide Astra’s supervision while the VLA carries out substantial portions of execution without additional review.

2 Related work

Foundation models for robot control.

Language and vision-language models connect high-level task reasoning to robot execution through affordance-based skill selection, robot API programs, and spatial objectives for motion planning [9, 11, 14]. VLAs learn action prediction from robot demonstrations and pretrained representations [1, 13, 21], while RoboICL and GPT-Policy explore general-purpose VLM control from demonstrations and feedback without deployment-time weight updates [4, 15]. The direct Astra policy generates Cartesian waypoints using sampled episode history on RoboMME [12]. In our system, a trained VLA handles routine execution, while Astra can directly intervene when needed.

Hierarchical execution and feedback.

Inner Monologue incorporates environmental feedback into language-based planning [10]. PonderPounce uses a multimodal model to maintain episode context and guide a fast VLA, while τ0\tau_0-VLA combines execution memory with world-model-guided subtask selection [2, 5]. The three-tier Astra system uses a fine-tuned Qwen3-VL-4B monitor to detect subtask completion and trigger the next Astra planning call, while a fine-tuned π0.5\pi_{0.5} executes the subtasks [3]. In contrast, our harness allows Astra to schedule execution reviews and configure auxiliary monitors that can trigger earlier inspection. Beyond subtask completion, Astra can assess execution errors and intervene directly when recovery is needed.

Task memory and experience reuse.

RoboMME evaluates manipulation that depends on past observations [6]. Relevant memory mechanisms include SAM2Act+’s visual memory bank, MEM’s short-horizon video and long-horizon text, SimpleMemVLA’s sampled video context, and MemER’s retrieval of task-relevant historical keyframes [7, 17, 18, 20]. Our harness uses archived images and episode notes to maintain task context within an episode, while separately accumulating experience to guide decisions in future episodes.

Beyond within-episode memory, Reflexion uses textual feedback to improve subsequent attempts, Voyager accumulates reusable skills through interaction, and ME-Brain-1.0 consolidates embodied experience for future decisions [8, 16, 19]. Our persistent store contains conditional execution advice that Astra can revise after an episode. This experience guides subgoal planning, review timing, and recovery decisions, with recommendations tied to their supporting evidence and applicable conditions.

3 Harness

3.1 System and task context

The harness connects Astra’s task decisions to VLA execution and direct intervention (Figure 2). At each decision point, Astra receives the task instruction, current front and wrist RGB images, robot state, and a summary of the next action sequence predicted by the VLA. It can query archived observations and consult episode notes. Relevant global and task experience remains available throughout the episode. Forward kinematics is used to estimate the end-effector motion implied by the VLA’s predicted joint actions. Episode success is determined by official environment feedback.

Figure 2. Astra sets execution budgets and selects monitors while the VLA reacts to new observations. Direct interventions bypass the VLA; post-episode review revises advice for later decisions.

The VLA uses the official RoboMME GroundSG checkpoint and maps its current observation and grounded subgoal to a joint-action sequence. Astra can permit one action chunk, let the VLA execute several chunks before review, or directly specify end-effector targets in world coordinates and gripper commands. Direct intervention bypasses the VLA but acts on the same robot and episode. After a subgoal change or direct intervention, the VLA predicts a new action sequence from the latest observation and current subgoal before execution resumes.

History queries recover evidence absent from the current views, including reset demonstrations and intermediate observations. Astra first samples a requested interval, including its endpoints, then narrows the interval or inspects original frames when necessary. Episode notes retain task-relevant interpretations and unresolved hypotheses with frame references, allowing Astra to revisit their supporting observations when needed. The agent uses task instructions, front and wrist images, and robot state available under standard RoboMME evaluation. It receives no privileged environment information such as ground-truth object states or oracle subgoals.

3.2 Grounded subgoals

A grounded subgoal combines a RoboMME task template, semantic attributes, and target image points [6]. Astra resolves the attributes from history and the current scene; the harness converts normalized points to front-image pixel coordinates and inserts them into the instruction. For example, an InsertPeg grasp specifies the near or far end of the peg and its image location:

pick up the peg by grasping the near end at <128, 64>

The coordinates here are illustrative image references. Insertion additionally specifies the left or right side of the box. The VLA receives this grounded instruction with the task instruction, current images, and robot state, matching the representation used in its RoboMME training annotations. Applicable experience can advise target selection or recovery, while Astra judges whether its conditions fit the scene. Experience can therefore influence which subgoal is selected without changing the task requirements or the controller’s instruction vocabulary. Appendix C gives conversion and validation details.

3.3 Execution delegation and recovery

To avoid unnecessary reviews during routine execution, Astra assigns a finite execution budget based on current observations, task history, and relevant experience. Initial budget advice comes from the number of control steps used to complete subtasks in training demonstrations; the lower quartile of each subtask’s duration distribution provides a starting point. Subsequent experience refines these recommendations for particular stages and observed execution difficulties.

Longer execution intervals can be paired with auxiliary monitoring tools. Gripper-state changes, directional displacement beyond a specified threshold, or a lack of end-effector movement can indicate a stage transition or potential execution problem. Astra selects the relevant monitors when assigning a budget. A detected condition prompts visual review, allowing Astra to inspect progress before the full interval ends. These tools let Astra retain longer budgets during routine motion while watching for events that may require attention. Thresholds and implementation details appear in Appendix A.

After executing these steps, the VLA predicts the next action chunk from the latest observations. Thus the controller continues to respond to the scene while Astra reviews at the selected interval or when a monitor triggers.

At a nonterminal review with a valid execution state, Astra compares the new observations with the intended subgoal and relevant history. It can extend execution, choose another subgoal, permit one chunk at a time for close supervision, or intervene directly. For example, an incorrect target may call for another history query and a revised subgoal, whereas a stalled contact motion may call for a local end-effector correction. After intervention, the VLA receives the resulting observation and resumes control under Astra’s next decision. Budgeted execution and event-triggered review therefore support both sustained VLA operation and targeted recovery.

3.4 Cross-episode experience evolution

The experience store captures what Astra learns about task interpretation and VLA execution across episodes. Entries pair an observation or recommendation with its applicable conditions and supporting frames. Advice can concern target identification, review intervals, monitoring choices, or recovery. Revisions replace outdated recommendations while preserving their earlier versions. Each episode uses the available global and task-specific experience, and new findings become available to subsequent episodes.

After the episode ends, Astra performs the review in the same agent session. Its inputs include retained interactions and tool responses, episode notes, active experience, and the official outcome and termination status. It can query archived front and wrist images, moving from sparse sampling to closer inspection. Execution records include the selected budgets, the number of steps executed, and the conditions that prompted review. Astra uses these records to identify problematic stages, assess its earlier supervision and recovery decisions, and determine whether the findings should update existing experience.

Astra adds an entry when review identifies a transferable finding, or revises an existing entry when new evidence changes its recommendation or applicable conditions. Findings already covered by the store require no update. For example, hovering observed before a scheduled review can motivate a shorter budget for that phase or the use of a stationary-motion monitor. A recommendation that works for one temporal query can be revised to distinguish before-event and after-event tasks. In this way, experience develops from individual outcomes into conditional guidance for later decisions.

Updates pass structural and scope checks before entering the experience store. Later decisions can cite the relevant entries when choosing a subgoal, review interval, or recovery action, making it possible to trace how past outcomes informed subsequent actions (Section 5). Adaptation takes place through this evolving context while the VLA weights remain fixed.

4 Experimental setup

Benchmark and adaptation.

We evaluate the official RoboMME test split: 16 tasks across Counting, Permanence, Reference, and Imitation, with 50 episodes per task and 800 in total [6]. Episode seeds and difficulty follow the benchmark specification; official environment feedback determines success. We use GPT-6 Astra as the supervisor and the official RoboMME GroundSG checkpoint, a grounded-subgoal π0.5\pi_{0.5} policy, as the VLA. The VLA weights remain fixed. Initial experience consists of duration recommendations derived from subtask completion-step statistics in training demonstrations. In every task, the first five episodes permit experience updates after either outcome; the remaining 45 permit updates only after unsuccessful outcomes. All 50 episodes contribute to the reported success rate. The experience store remains fixed within each episode, and accepted revisions are made available to subsequent episodes. Appendix A specifies model settings, limits, and cross-task sharing.

Observation access.

The harness uses the task instruction, front and wrist RGB images, and robot state available to the VLA under standard RoboMME evaluation. Historical observations come from the same observation stream. Planning and control receive no privileged environment ground truth, such as hidden object states or oracle subgoals. Official success and termination feedback is used for outcome assessment and post-episode review.

Comparisons.

Table 1 groups learned policies, direct VLM control, and hierarchical systems, reporting overall success [3, 5, 6, 12, 17, 20]. Human skill selection and GroundSG+Oracle are separate privileged references. PonderPounce-9B uses the reported standard-data leaderboard result, and the other reference scores follow the cited benchmark and system reports; controller training, history access, intervention interfaces, and test-time experience updates differ across systems. We additionally compare delegation with per-chunk review on ten StopCube test seeds. Both conditions are rerun with the same models, history tools, recovery interfaces, and execution limits. Within each pair, both read the same saved version of the experience store, and experience updates are disabled. Runs are serial, with the order of conditions alternating across pairs. This comparison isolates review policy under a fixed experience context for each seed.

Measurements.

We report task success and the distribution of control steps across four execution modes: subgoal entry, Astra intervention, automatic VLA continuation, and VLA continuation after review. The last mode is the first VLA chunk released after Astra checks progress on the current subgoal; subsequent chunks within the same budget count as automatic continuation. Completion time includes model inference, history queries, action execution, and waiting. Completion-time statistics are reported for successful episodes, since failed runs may terminate early or continue until the execution limit. Appendix D gives detailed accounting.

5 Results and analysis

5.1 Task performance

The harness succeeds in 777 of 800 episodes (97.1%; Table 1), exceeding the published direct-Astra and three-tier Astra scores by 5.0 and 18.0 percentage points, respectively. Success reaches 97.0% on Counting, 97.5% on Permanence, and 97.0% on both Reference and Imitation. Every task achieves at least 90%, and seven reach 50/50 successes. Gains over direct Astra are particularly large on MoveCube (100% versus 54%) and StopCube (96% versus 54%). The task results in Figure 3 show that the combined system performs well across all four memory categories.

5.2 Supervision and execution efficiency

Automatic VLA continuation accounts for 54.93% of control steps, allowing more than half of execution to proceed without additional Astra review (Table 2). Astra intervenes directly in 33.5% of episodes, but these interventions account for only 4.91% of control steps. Most motion therefore remains with the learned controller, while Astra contributes local corrections when needed.

Review frequency adapts to the demands of each task. Insertion involves error-prone contact and alignment, so InsertPeg often requires close inspection and corrective action. RouteStick instead contains short directional subtasks; Astra tends to permit one chunk at a time to avoid continuing past a subtask boundary. In VideoPlaceButton, Astra can allow longer execution intervals once the target has been identified. These patterns suggest that review needs vary across task stages, with some stages requiring closer supervision than others.

Appendix E reports full-benchmark completion times. We use a matched comparison to examine the effect of review frequency on execution time and model usage.

Matched review-policy comparison.

Delegation reduces completion time on the nine StopCube seeds that succeed under both review policies (Table 3). Mean execution time falls from 513.2 to 285.6 s, a reduction of 44.3%, and delegation is faster in all nine pairs. Across all ten seeds, the two conditions execute similar numbers of control steps, while delegation automatically continues 57.6% of execution requests and reduces total input tokens by 60.7%. Per-chunk review succeeds on 10/10 seeds and delegation on 9/10. This comparison shows that delegation can substantially reduce execution time and token usage, although it fails on one seed completed successfully by per-chunk review.

5.3 Execution and experience analysis

Across the evaluation, Astra updates the experience store after 37 episodes, producing 43 entries, including seven revisions of earlier advice. Later execution decisions explicitly cite 38 of these entries across 468 episodes. The cases below show how this reused experience changes review intervals and target interpretation, helping Astra adapt its supervision to the VLA’s observed behavior.

Revising execution advice.

In PickXtimes, Astra observes hovering during button pressing and subsequently adds a stationary-motion monitor to the recommended 90-step budget. In the next episode, execution again reaches the 90-step budget without triggering the monitor. The recorded motion never satisfies the 2 mm stationary threshold over a 32-step window: the smallest position diameter is 26.9 mm. Astra revises the advice to 60 initial steps, with review intervals of at most 16 steps during contact or recovery. In the following episode, Astra explicitly cites the revision and sets a 60-step budget with the stationary-motion monitor enabled. The VLA executes four chunks of 16, 16, 16, and 12 steps before budget exhaustion; Astra then permits another action chunk, which completes the task after 13 steps. Figure 4 illustrates this revision and subsequent execution. The revised advice brings visual review forward while retaining stationary-motion monitoring as another way to trigger review.

Revising historical interpretation.

In VideoPlaceButton, a failed episode leads to advice for tracking visually similar rings through late demonstration swaps, but the resulting recommendation incorrectly assumes a before-press query. In the next episode, the task asks for the first event after the press; Astra recognizes that the earlier rule does not apply and subsequently revises it to condition on the current temporal query. A later episode asks for the last event before the press. Astra explicitly cites the revision in its notes and execution decision, examines the relevant historical frames, and selects the topmost ring. With an 80-step budget, the VLA completes the task after 54 steps. The revision preserves the identity-tracking advice while making target selection conditional on the requested temporal relation (Figure 5).

5.4 Failure analysis

We manually inspect all 23 failed episodes and group their primary causes into historical interpretation (8), subgoal grounding (1), execution (9), and review or recovery (5).

Specifically, historical interpretation accounts for all five VideoPlaceOrder failures and also affects VideoPlaceButton and InsertPeg. The RouteStick grounding error concerns the task’s left–right convention. Execution problems include insufficient endpoint motion in two SwingXtimes episodes and insufficient container lift in one VideoUnmaskSwap episode. Two ButtonUnmaskSwap episodes advance before the button action is complete, and the two StopCube failures involve early or missed button timing. Repeated alignment and contact recovery also leave some InsertPeg episodes unsuccessful. These cases identify where history interpretation, progress review, and local correction still need improvement; representative trajectories appear in Figure 7, with further details in Appendix H.

6 Discussion and limitations

Despite high task success and less frequent Astra review, the harness has several limitations. On-demand history queries avoid including the entire observation history in every Astra reasoning context. Sparse sampling can nevertheless omit a brief event or a late target swap, leading Astra to choose the wrong subgoal. More targeted retrieval of historical observations could reduce these errors without requiring the entire history to be included in the context.

Experience revision allows Astra to correct advice after new outcomes, yet an incorrect recommendation can still influence subsequent decisions before it is revised. The current store also has no explicit bound on the amount of accumulated advice. As the store grows, redundant or conflicting recommendations may increase context usage and make it harder to select appropriate advice. Retrieval and consolidation that retain useful distinctions while removing redundant advice are natural extensions.

Reducing review frequency addresses only part of the execution overhead. Each Astra decision still requires remote model inference, introducing latency whenever execution pauses for supervisory review. Faster supervisory inference and more selective invocation remain important for approaching the responsiveness of a standalone VLA policy.

7 Conclusion

We present a self-evolving harness that uses execution experience to guide Astra’s supervision of a learned manipulation policy. Across 800 episodes on all 16 RoboMME tasks, the system achieves 97.1% success, with 54.9% of control steps executed without additional Astra review. These results illustrate how accumulated execution experience can inform Astra’s review, task interpretation, and recovery decisions, while allowing the VLA to handle most low-level control.

Robot-state monitors.

The measured gripper monitor detects a total finger-width change of at least 5 mm from the start of the execution interval, sustained for two measured samples in the same direction. The direction monitor checks predicted or measured displacement greater than 20 mm in a selected signed world-frame direction relative to the robot pose at the start of the execution interval. The stationary-motion monitor uses a position diameter of at most 2 mm and an orientation diameter of at most 2∘2^\circ over 32 control steps. An impending gripper-command switch can also trigger review. Astra selects the active monitors for each execution interval. Budget exhaustion prompts review, and episode termination stops execution.

C Interface and experience details

Observation provenance.

Image-delivery records distinguish the visual evidence included in each successful Astra request from observations available only through retrospective inspection of the full recording.

Grounding.

For a front image of height HH and width WW, a normalized point (yn,xn)∈[0,1000]2(y_n,x_n)\in[0,1000]^2 is converted to

y=min(⌊ynH/1000⌋,H−1),x=min(⌊xnW/1000⌋,W−1).y=\min(\lfloor y_nH/1000\rfloor,H-1),\qquad x=\min(\lfloor x_nW/1000\rfloor,W-1).

(2)

The pixel coordinates replace the instruction’s ordered point slots. Validation checks finite coordinate values, normalized bounds, the number of supplied points, and compatibility with the task’s templates and permitted attributes. Astra can inspect an overlay before setting the subgoal. The default sparse history query selects up to eight uniformly spaced frames, including interval endpoints.

Control steps and duration priors.

A control step is counted at the shared environment action interface, separately from simulator integration steps. At environment frequency fc=20Hzf_c=20\,\mathrm{Hz}, nn steps correspond nominally to n/fcn/f_c seconds of simulated control. Inference and API waiting time contribute separately to elapsed time. Repeated training samples are deduplicated by task, episode, and timestep before consecutive identical subgoal labels are grouped. Segment lengths are estimated from timestep differences. For lengths DsD_s associated with subgoal ss, the initial recommendation is

B̂s=min(200,10⌊Q0.25(Ds)/10⌋).\widehat B_s=\min\!\left(200,10\left\lfloor Q_{0.25}(D_s)/10\right\rfloor\right).

(3)

Recommendations below 30 control steps become advice for close review. Because sampled annotations may miss short segments or include trailing frames in terminal segments, these duration estimates serve as initial guidance rather than exact subtask boundaries.

Experience validation and applicability.

Submission checks cover required fields, permitted scope and applicability labels, cited frame indices, and the existence of superseded identifiers. Scheduling advice is also checked for compatibility with subgoal templates and valid monitor parameters. Experience entries are marked as either policy-independent or specific to a review policy. When retrieving advice, the harness first selects entries applicable to the current policy and then resolves superseded recommendations. The optional scheduling field max_trust_steps records a recommended review interval; the configured execution maximum remains the enforced limit.

D Measurement definitions

Success rate is the number of officially successful episodes divided by the evaluated count. Equal task sizes make overall success equal to the mean task success rate. Execution-time summaries include only the 777 successful episodes; token totals include all 800 episodes. API attempts and elapsed time include failed requests. Token statistics report coverage of returned usage; cached input is a subset of total input, and missing usage remains unknown. Execution and post-episode revision token totals are reported separately. API latency for revision is not a measurement of the complete revision wall time.

Automatic continuation counts VLA chunks executed after the first chunk of an execution interval. The all-chunk fraction divides these by all executed VLA chunks. The automatic-control fraction divides control steps in continuation chunks by all executed control steps, including direct interventions. Fractions use pooled counts across episodes rather than averages of episode percentages.

H Failure annotation and reference-frame clarification

Manual inspection of the 23 unsuccessful episodes assigns one primary label per episode: historical interpretation (8), subgoal grounding (1), execution (9), or review and recovery (5). The execution category includes two SwingXtimes episodes in which the motion does not fully reach the target and one VideoUnmaskSwap episode with insufficient container lift. Each episode is counted once according to its primary failure mode.

In the first RouteStick episode, Astra misinterprets the task’s left–right convention, leading to an incorrect directional subgoal. As RoboMME’s directional instructions do not explicitly specify the reference frame, we subsequently added a clarification of this convention to the agent’s global experience context: task directions refer to the initial wrist view or initial robot orientation, rather than the changing wrist orientation or the front-view screen axes. Image points retain the pixel coordinates of their own camera. This interface clarification is not counted among the 37 autonomous experience updates.

I Review-policy comparison

The StopCube comparison uses ten official test seeds, with both policies rerun under the same harness configuration. The two conditions receive identical saved versions of the experience store within each pair. Experience updates are disabled to keep the comparison focused on review policy. Runs alternate which policy executes first.

Delegation is faster on all nine jointly successful seeds, saving a mean of 227.6 seconds. The first per-chunk run includes 35.5 seconds of VLA inference, compared with 2.3 seconds for its delegated counterpart. Excluding this pair leaves eight joint successes with mean times of 491.9 and 280.6 seconds, respectively, a 43.0% reduction. Across all ten runs, execution uses 2,021 control steps with per-chunk review and 2,010 with delegation. Input-token totals fall from 30.63 to 12.05 million; uncached input falls from 2.22 to 1.19 million, and output from 32,222 to 21,333 tokens.
